## R2-04 — A wrong expense can never be fixed or deleted; the only way to add one is permanent.

- **Roadmap:** 101.1
- **Severity:** before
- **Category:** opportunity
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — The expense rows at app/src/screens/Money.jsx:999-1024 are plain divs with no onClick; the only button is the receipt thumbnail, which opens the receipt viewer. The only app write to the expenses table is the insert at app/src/components/ExpenseModal.jsx:124-131 (receipts.js only touches receipt fields), and Money.jsx:1063-1068 itself says the sheet 'is add-only ... there is no way to reopen a saved one'. No open ROADMAP item covers editing or deleting an expense; the closest open items are 97.29 (row cap) and 4.1 (job undo), and neither is about this.
- **Supposed to:** A detailer who typed $1,890 instead of $189 should be able to correct or remove the expense so profit is right.
- **What the code does:** The expense list rows are plain text (no tap action) and the only code that writes to the expenses table is the insert in ExpenseModal. The Money screen's own comment says the sheet is add-only. Receipts can be removed, the expense itself cannot.
- **What happens:** One slip of the thumb on a phone number pad permanently lowers 'Earned less expenses' and the accountant export for that month, and the detailer has no way to correct it short of contacting support.
- **Fix:** Make each expense row open the same sheet with the saved values, with Save changes and a ConfirmTap Delete.
- **Reproduce:** Money > Expenses > Add, save any amount, then try to tap the new row: nothing opens.
- **Impact:** Every detailer who logs expenses; wrong profit and wrong tax export with no fix.
- **Benefit:** Profit figures and the export can be corrected, which is the job this screen exists for.
- **Effort:** medium
- **Risk of fixing:** low
- **Confidence:** high
- **Evidence:**
  - file: `app/src/screens/Money.jsx:997-1028`
  - file: `app/src/components/ExpenseModal.jsx:120-131`

## R2-05 — The expense form accepts a negative amount, which would raise profit instead of lowering it.

- **Roadmap:** 101.2
- **Severity:** before
- **Category:** defect
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — ExpenseModal.jsx:201-209 is a type=number input with no min, and both the guard at :121 and the disabled check at :284 use !Number(amount), which lets -50 through; :129 inserts Number(amount) as is. The expenses.amount column at 20260827000200_tenant_data.sql:342 is 'numeric not null' with no check, and no later migration adds one. No open ROADMAP item covers it; 97.31 and 97.34 are about promo discounts and formatting.
- **Supposed to:** An expense is money that went out, so the amount should be more than zero.
- **What the code does:** The amount box is a number input with no minimum, and Save is enabled for any non-zero number, so -50 passes. The column is 'numeric not null' with no check that it is above zero.
- **What happens:** Pressing the minus key on a phone number pad (or a pasted -189) records a negative expense: 'Earned less expenses' goes up and the accountant file shows a positive line.
- **Fix:** Add min="0" and require Number(amount) > 0 in the Save check, and add a check (amount > 0) on the table.
- **Reproduce:** Money > Expenses > Add, type -50, pick a category: Save expense is enabled and saves.
- **Impact:** Anyone mistyping an amount; wrong profit and export. I did not check later migrations or server rules for a guard.
- **Benefit:** Stops a bad number reaching the profit figure.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** medium
- **Evidence:**
  - file: `app/src/components/ExpenseModal.jsx:201-209`
  - file: `app/src/components/ExpenseModal.jsx:121`
  - file: `app/src/components/ExpenseModal.jsx:284-285`
  - file: `supabase/migrations/20260827000200_tenant_data.sql:342`

## R2-06 — On Promo codes, 'Code added' and error messages appear below the whole list, and failures to switch a code on or off are never shown.

- **Roadmap:** 101.3
- **Severity:** before
- **Category:** defect
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — Promos.jsx:308 draws the one shared msg box after the codes list (279-306), below both the Save sale (201) and Add code (271) buttons; addCode shows the raw Supabase error.message on failure (118), so a duplicate code shows Postgres's 'duplicate key value violates unique constraint' text. toggleCode (124-127) ignores the update's error and just reloads, and load (97-100) ignores its error too, so a failed load and having no codes both render nothing because of the codes.length > 0 check at 279. No open ROADMAP item covers this; the promo items 97.9, 97.23 and 97.31 are about pricing and booking.
- **Supposed to:** After pressing Save sale, Add code or Deactivate the detailer sees straight away whether it worked, in plain words.
- **What the code does:** One shared message is drawn at the very bottom of the screen, under the Your codes list (and the 390px screenshot shows the Save sale and Add code buttons are 400-700px above it). A duplicate code prints the database's own message, not a sentence. toggleCode awaits the update but ignores its error, and the list has no loading or 'no codes yet' state (a failed load looks the same as no codes).
- **What happens:** A detailer taps Add code, nothing visible changes where they are looking, so they tap again or give up; a duplicate code shows text like 'duplicate key value violates unique constraint'; a Deactivate that failed looks like it did nothing.
- **Fix:** Draw the message directly under the button that was pressed (two messages: sale and code), replace the duplicate error with 'You already have a code called X', check the error in toggleCode, and show a short 'No codes yet' line.
- **Reproduce:** At 390px open Settings > Promo codes, add the same code twice: the red box appears under the whole codes list, outside the first screen's view, and reads as a database error.
- **Impact:** Any detailer setting up promos on a phone.
- **Benefit:** Feedback is seen and understood; no more guessing whether a sale or code is live.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** high
- **Evidence:**
  - file: `app/src/screens/more/Promos.jsx:118`
  - file: `app/src/screens/more/Promos.jsx:124-127`
  - file: `app/src/screens/more/Promos.jsx:279-306`
  - file: `app/src/screens/more/Promos.jsx:308`

## R2-07 — If 'Your subscription' cannot load, the detailer sees a raw error with no way to try again.

- **Roadmap:** 101.4
- **Severity:** before
- **Category:** defect
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — Billing.jsx:162-168 catches the summary failure and stores String(e.message), and Billing.jsx:311 then renders only that text in an error box with no button and no call back to load(); Billing.jsx:324-329 shows 'Checking your subscription…' indefinitely because fetch in book/core.js:44-73 has no timeout. The message is raw: core.js:62 passes through the server's error text or 'Request failed (503)', and with no signal the browser's 'Failed to fetch' reaches the screen unchanged; act/start/confirm (Billing.jsx:184,287,307) show raw messages the same way. No open ROADMAP item covers it (6.4 is about offline schedules and duplicate retries, 97.48 is the booking page only).
- **Supposed to:** A billing screen that fails should say so in plain words and offer Try again.
- **What the code does:** load() stores String(e.message) and the screen then draws only that text in an error box. There is no retry button and no timeout on the 'Checking your subscription…' state. Every other billing error (subscribe, cancel, card refused) is also shown as the raw message.
- **What happens:** The Billing screenshot at 390px is a single grey line 'Checking your subscription…' with nothing else; if the server answers with an error (cold start, no signal) the detailer sees whatever text it sent and must leave and re-enter the screen. This is the page they open when they are worried about a charge.
- **Fix:** Show a fixed sentence ('We could not load your subscription.') plus a Try again button that calls load(), and keep the server's text only as small detail.
- **Reproduce:** Open Settings > Your subscription with the network blocked to the billing function: you get an error box and no button.
- **Impact:** Detailers checking a charge, or paying, when the connection is poor.
- **Benefit:** A recoverable billing screen and fewer support calls.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** medium
- **Evidence:**
  - file: `app/src/screens/more/Billing.jsx:162-169`
  - file: `app/src/screens/more/Billing.jsx:311`
  - file: `app/src/screens/more/Billing.jsx:324-329`

## R2-08 — Several money screens print some sentences in English on a Spanish dashboard.

- **Roadmap:** 101.5
- **Severity:** before
- **Category:** defect
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — Billing.jsx:411-412, 428, 582 ('Code {promo.code}'), 883 ('You committed to {n} months') and 896-898 (the cancel 'After that your booking page stops taking new bookings...' sentence) are bare JSX text outside t(), and Payments.jsx:272 shows a hard-coded 'Saved.' and the raw error.message. The Money.jsx part is overstated: periodAt (lib/periods.js:53-95) builds week/month/6m labels with the app locale, so only the lifetime label 'All time' (periods.js:107) leaks English into Money.jsx:992 and :1036; the ', and ' fragment at Billing.jsx:588 does go through t(). No open ROADMAP item covers it, and English on the screen that explains charges and cancellation is a real defect a Spanish-speaking paying detailer would hit, so 'before' rather than 'after'.
- **Supposed to:** Every sentence on the dashboard goes through t() so a Spanish dashboard reads in Spanish.
- **What the code does:** These strings are bare JSX or template text: Billing's 'Everything you have already set up stays exactly as it is…', 'Every one of these also includes the one-time', 'Code {promo.code}', 'You committed to {n} months', 'After that your booking page stops taking new bookings…', Payments' 'Saved.' and the raw error.message, Money's expense heading and 'more in' line use period.label without t(), and Billing builds sentences from fragments (', and ').

- **Reproduce:** Switch the dashboard language to Spanish and open Your subscription (not subscribed) and Cancel.
- **Impact:** Spanish-language detailers; cancellation and charge wording is the most important to understand.

## R2-09 — How you get paid and the sale switch lose changes if you leave without pressing Save, and some controls act without warning.

- **Roadmap:** 101.7
- **Severity:** after
- **Category:** improvement
- **Area:** Money
- **Found by:** looks auditor (claude-sonnet-5-5)
- **Second check:** confirmed by opus — Payments.jsx:431-433 (Venmo/handle switches), :497 (Remove, no confirmation) and :506/:516 (custom switch/handle) only change local state; nothing is written until save() at :237-275, which runs only from the bottom Save button at :573, and the app has no unsaved-changes guard (no beforeunload/useBlocker/dirty flag anywhere in app/src). Disconnect uses the browser's native confirm() at :233, and Promos.jsx:180-184 sets only local sale state, saved only by the separate 'Save sale' button at :201 via saveSale at :129. No open ROADMAP item covers it; severity 'after' fits because nothing saved is lost or corrupted, the change just doesn't happen.
- **Supposed to:** A settings screen should either save as you go or clearly show there is something unsaved.
- **What the code does:** On How you get paid, switches, handles and Remove on a custom method only change local state until the Save button at the very bottom, with no unsaved marker. Remove on a custom method has no confirmation. Disconnecting Stripe uses the browser's native confirm() box, unlike the app's own ConfirmTap and Sheet. On Promo codes the 'Sale is running' switch only takes effect after a separate outlined Save sale button, which sits well below it.
- **What happens:** A detailer who flips Venmo on, types the handle and goes back with the arrow, or switches a sale on and moves on, has changed nothing: customers still see the old payment options or no sale, and nothing said so.
- **Fix:** Save the sale switch and the payment switches as they are changed (or show 'Unsaved changes' and warn on back), use ConfirmTap for Remove and Disconnect, and make Save sale a primary button next to its group.
- **Reproduce:** At 390px open How you get paid, switch Venmo on, type a handle, press the back arrow, reopen: the handle is gone.
- **Impact:** Detailers setting up how customers pay them or running a sale.
- **Benefit:** What the screen shows is what customers are shown.
- **Effort:** medium
- **Risk of fixing:** medium
- **Confidence:** medium
- **Evidence:**
  - file: `app/src/screens/more/Payments.jsx:233`
  - file: `app/src/screens/more/Payments.jsx:495-499`
  - file: `app/src/screens/more/Payments.jsx:573`

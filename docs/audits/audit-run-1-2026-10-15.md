## R1-03 — A staff member whose 'Answer requests' permission was switched off can still accept or decline booking requests.

- **Roadmap:** 100.1
- **Severity:** before
- **Category:** defect
- **Area:** Booking
- **Found by:** code auditor (opus)
- **Second check:** confirmed by claude-sonnet-5-5 — update-booking/index.ts:85 only calls requireMember (tenant.ts:304 checks membership only, no permission) and never can(member,'requests'); line 55 allows 'status' and lines 116-118 write it, with justCancelled (226) emailing the customer. respond-to-booking/index.ts:44 does gate on can(member,'requests') with a 403, so the permission is bypassable through the general path. No open ROADMAP item covers it (97.14 is about direct browser deletes/edits, a different problem).
- **Supposed to:** 'Answer requests' is the permission an owner can take away from staff; respond-to-booking refuses anyone without it.
- **What the code does:** update-booking lets any member of the business write the status field (it only checks membership, never can(member, 'requests')). Since browsers cannot update bookings directly, this is the one write path, and it accepts status 'confirmed' or 'cancelled' on a pending request.
- **What happens:** Staff the owner deliberately blocked from answering requests can confirm one (the customer gets no acceptance email) or cancel it (the customer gets a cancellation email), simply through the general status change. The owner's permission setting does not hold.
- **Fix:** In update-booking, when the current status is 'pending' and the new status differs, require can(member, 'requests') (or send that transition to respond-to-booking); return 403 otherwise.
- **Reproduce:** As a staff member with permissions [] on a request-mode business, call update-booking with { booking_id: <pending id>, status: 'confirmed' }. It succeeds, whereas respond-to-booking with action 'accept' returns 403.
- **Impact:** Owners who use custom roles; a request can be accepted or turned away by someone not allowed to, and the customer is told the wrong thing or nothing.
- **Benefit:** The permission means what the Team screen says it means.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** high
- **Evidence:**
  - file: `supabase/functions/update-booking/index.ts:54-56`
  - file: `supabase/functions/update-booking/index.ts:85-86`
  - file: `supabase/functions/update-booking/index.ts:116-118`
  - file: `supabase/functions/respond-to-booking/index.ts:44-46`
  - file: `app/src/lib/permissions.js:33-38`

## R1-01 — When a customer presses Confirm again after a dropped connection, the confirmation screen shows a broken date, no times and a dead 'change or cancel' link.

- **Roadmap:** 100.2
- **Severity:** before
- **Category:** defect
- **Area:** Booking
- **Found by:** code auditor (opus)
- **Second check:** confirmed by claude-sonnet-5-5 — Both duplicate exits (create-booking/index.ts:263 and :592) return `{ booking: mine, duplicate: true }` where `mine` is the raw select("*") row (:65-75), while the fresh path (:773-787) builds booking_date, start_time, end_time, total_price and receipt_url. BookingPage.jsx:552 passes r.booking straight to BookingConfirmed, which reads booking.booking_date (:19-21 gives Invalid Date), start_time/end_time (:71) and receipt_url (:88, href undefined); no client-side mapping or guard exists. ROADMAP 97.2 covers the data leak on the same lines but its fix (return only id, start time, status) would leave this display bug, so it does not cover this problem.
- **Supposed to:** The code says a retry of a booking that already landed must get 'the SAME shape a fresh booking returns', so the confirmation screen and links behave identically.
- **What the code does:** Both duplicate exits return the raw database row from select("*"). That row has start_at/end_at but no booking_date, start_time, end_time or receipt_url, which are the fields the fresh path builds and the confirmation screen reads. The raw row also carries every internal column (admin notes, payment fields) to a public caller.
- **What happens:** On the bad-connection retry this was built for, the customer sees 'Invalid Date' as the heading, blank start and end times, and a 'View, change or cancel this booking' button with no address. They cannot reach their manage page from the screen and may think the booking failed and book again.
- **Fix:** In both duplicate branches return the same object the success path builds (id, booking_date and times in business time, total_price, receipt_url, status) instead of the raw row; a small helper shared by all three exits keeps them identical.
- **Reproduce:** Make a booking, then POST the identical create-booking payload again (same name, phone, date, time). The response has duplicate:true and a booking object with no booking_date, start_time or receipt_url; render BookingConfirmed with it.
- **Impact:** Every customer whose first submit response is lost, which is the common mobile case the retry logic exists for; risk of double bookings and support calls.
- **Benefit:** The retry path becomes truly invisible to the customer, and internal booking fields stop leaving the server.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** high
- **Evidence:**

  - file: `supabase/functions/create-booking/index.ts:258-265`

## R1-02 — The public price-quote endpoint can spend the shared address-lookup allowance for every detailer, without the limits that protect it.

- **Roadmap:** 100.3
- **Severity:** before
- **Category:** defect
- **Area:** Booking
- **Found by:** code auditor (opus)
- **Second check:** confirmed by claude-sonnet-5-5 — calculate-booking/index.ts:180-186 calls pointFor on the customer's address, and weatherCache.ts:68-73 geocodes any uncached address through suggest() with no address-specific limit. The only guard in calculate-booking is the generic 600 per IP per hour (index.ts:36, rateLimit.ts:141), and address-suggest's address_day bucket (address-suggest/index.ts:82) is never touched by this path. The code comment at index.ts:110 says it never calls a provider, which is wrong for unseen addresses; ROADMAP.md:4346 even notes the credit spend but no open item covers it.
- **Supposed to:** Address lookups (Geoapify) are metered and shared by every tenant, so address-suggest caps them at 60 per IP per hour and 2,400 per day in total. The quote endpoint's own comment says its weather line 'never calls a provider'.
- **What the code does:** calculate-booking calls pointFor on whatever customer_address it is sent once a date and time are present. pointFor geocodes any address not already cached by calling suggest() directly, with no address-specific limit; the only guard is the generic 600 calls per IP per hour. The booking page also sends a fresh quote on every keystroke when a customer goes back to edit the address after picking a day.
- **What happens:** One script, or a few customers correcting addresses, can use up the day's lookup allowance. Once it is spent, address autocomplete stops working for every detailer's customers until the next day, and the daily counter in address-suggest never saw it coming.
- **Fix:** Make the weather line truly cache-only: in confirmWeather, read address_points and skip on a miss instead of calling pointFor (or pass a flag to pointFor that forbids the provider call). If a lookup is ever wanted there, put it behind the same addressPerIp and addressPerDay limits.
- **Reproduce:** POST calculate-booking with a valid slug, a service id, booking_date, start_time, service_type 'mobile' and a never-seen customer_address; repeat with new addresses. Each call adds an address_points row and spends one Geoapify credit, and the address_day bucket does not move.
- **Impact:** All tenants' customers lose address autocomplete for the rest of the day; the platform's Geoapify bill or quota is exposed to an unauthenticated caller at 600 lookups per hour per IP.
- **Benefit:** The shared allowance is spent only where it is counted, and the comment's promise becomes true.
- **Effort:** small
- **Risk of fixing:** low
- **Confidence:** high
- **Evidence:**

  - file: `supabase/functions/calculate-booking/index.ts:180-188`
  - file: `supabase/functions/_shared/weatherCache.ts:68-82`
  - file: `supabase/functions/address-suggest/index.ts:77-83`
  - file: `supabase/functions/_shared/rateLimit.ts:141`
